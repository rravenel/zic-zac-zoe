# Zic-Zac-Zoe: "Claim" Variant Specification

This update introduces the "Claim" mechanic, transforming the game from a static board-filling exercise into a dynamic, resource-management strategy game where the board state is constantly evolving.

## Core Rules Changes
- **Manual Scoring (The "Claim"):** Points are no longer awarded automatically. After placing a token, a player must choose to either "Claim" the points generated by that move or "Pass".
- **Resource Consumption:** When points are claimed, all tokens belonging to the **current player** that contribute to the scored lines are **removed** from the board. 
  - **Anchoring:** A claim is strictly tied to the move just played. Only lines that include the newly placed token are eligible for removal.
  - **No Manual Selection:** If a player chooses to claim, all valid lines connected to the move are processed and cleared automatically.
  - **Opponent Safety:** Opponent tokens are never removed by a player's claim.
- **Tactical Clearing:** Lines of length $L=3$ still award **0 points**, but claiming them will still remove the player's tokens. This allows players to clear the board of "dead" segments at the cost of forgoing a higher-scoring connection later.
- **Non-Termination:** Because pieces are removed, the board may never fill up. The game continues until a configurable win condition is met.

## Winning Conditions (Configurable)
The game supports multiple victory paths, controlled via a central configuration file. Only one mode should be active at a time. If multiple modes are set to `active: true`, the board will be hidden and replaced by a "CONFIGURATION ERROR" message in the center of the game area.

### 1. Point Cap
- **Condition:** The first player to reach a target score wins immediately.

### 2. Move Cap
- **Condition:** Each player is limited to a fixed number of moves. The game ends when both players have exhausted their moves. Placing a token counts as a move, regardless of whether points are claimed or passed.

### 3. Point Lead
- **Condition:** A player wins if they lead their opponent by a specific margin.
- **Safety Valve:** This mode is always backed by a **Per-Side Move Cap**. If the move cap is reached before the lead margin is met, the highest score wins.

### 4. Board Full (Automatic Termination)
- **Condition:** If a player places a token that fills the final open cell on the board:
  - The game ends immediately.
  - The points for that final move are **automatically claimed** for the current player.
  - **No tokens are removed** from the board, allowing the final state to be reviewed.
  - The player with the highest cumulative score wins.

## Configuration File (`game_config.json`)
A central configuration file allows tweaking the game balance without modifying source code.

```json
{
  "modes": [
    {
      "id": "point_cap",
      "active": true,
      "settings": { "target": 100 }
    },
    {
      "id": "move_cap",
      "active": false,
      "settings": { "limit_per_side": 50 }
    },
    {
      "id": "point_lead",
      "active": false,
      "settings": { "margin": 25, "limit_per_side": 100 }
    }
  ]
}
```

## UI & User Experience
- **Action Buttons:** The "Claim" and "Pass" buttons will replace the three setting buttons (`1P/2P`, `X/O`, `Difficulty`) in the lower-left controls area.
- **Scoreboard Relocation:** The scoreboard will be moved from the header and anchored directly above the game board. 
- **Mode Display:** The space created in the header (between the title and the board) will display the active game mode and its primary constraint (e.g., "Mode: Point Cap (Target 100)").
- **Sequence of Play:**
  1. Player places a token.
  2. The "Moves Remaining" counter for that player decrements immediately.
  3. The "Claim" and "Pass" buttons begin to **blink** to signal that a decision is required.
  4. Player either clicks "Claim" or "Pass".
  5. If "Pass" is clicked, the per-turn indicator shows `+0` to confirm the choice.
  6. The turn ends.
- **Visual Feedback:**
  - **Scoring Highlights:** Cells that contributed to a claimed score will be highlighted with a steady border. These highlights **persist** even after tokens are removed, remaining until the player's next turn.
  - **No Spoilers:** The UI will NOT pre-calculate or highlight potential points or removals.
- **Per-Turn Indicators:** Under each player's score on the scoreboard:
  - **Moves Remaining:** Displayed on the left (e.g., `M: 42`), left-justified.
  - **Points Earned:** Displayed on the right (e.g., `+5`), right-justified.
- **Animations:** Tokens should visually "evaporate" or fade out when claimed to signify they have been converted into points and the space is now free.

## AI & Opponent
- **Prototype Logic:** The AI will evaluate the points available for its move and make a probabilistic decision to Claim or Pass.
- **Claim Probability:**
  - `Points <= 1`: 50% chance to claim.
  - `Points >= 50`: 99% chance to claim.
  - `Between 1 and 50`: Probability scales linearly between 50% and 99%.

## Scoring Mechanics Consistency
The existing points-variant scoring logic is preserved:
- $L=1$: 1 point.
- $L=3$: 0 points.
- Other lengths: $L$ points.
- **Bridge Bonus:** 2x points if a move connects two existing segments.
- **Productive Multiplier:** Total score is multiplied by $N$ (number of axes producing $>0$ points).
